# Supabase: Agenda

Banco, autenticação e permissões da área **Agenda** e do painel. As migrations em `migrations/` são a fonte da verdade: nada deve ser alterado manualmente no dashboard.

## Configurar um projeto

1. Crie o projeto no Supabase e copie `.env.example` para `.env.local` (URL, publishable key e secret key).
2. Aplique as migrations, em ordem, escolhendo uma das opções:
   - **CLI:** `npx supabase init` (cria `config.toml` e mantém `migrations/`), `npx supabase link --project-ref <ref>` e `npx supabase db push`.
   - **Sem CLI:** cole cada arquivo de `migrations/` no SQL Editor, em ordem de nome, e execute cada um uma única vez (`20260929120000_agenda_infrastructure.sql`, `20260930120000_users_management.sql`, `20261011120000_videos.sql`, `20261012120000_show_models_sellers.sql`, `20261013120000_commercial_prices_video_placement.sql`, `20261014120000_remove_users_management.sql`, `20261015120000_agenda_public_toggle.sql`, `20261017120000_seller_links.sql`, `20261018120000_seller_role.sql`, `20261018120100_commercial_links_module.sql`, `20261018120200_short_link_codes.sql`, `20261018120300_remove_legacy_sellers.sql`, `20261019120000_corporate_prices.sql` e `20261020120000_channels_own_visibility.sql`). A `20261017120000` (links comerciais temporários) depende de `show_models`/`sellers` (`20261012120000`) e de `get_commercial_show_models` (`20261013120000`): aplique-a só depois delas e **antes** de publicar o código que a usa (ver "Links comerciais temporários" abaixo). As duas `20261018…` (papel SELLER e módulo Links comerciais) vão **juntas, nessa ordem, em execuções separadas** (o valor novo do enum só pode ser usado depois que a primeira termina) e antes do código que as usa (ver "Links comerciais por usuário" abaixo).
3. Regenere os tipos: `npm run db:types`. Isso sobrescreve `lib/supabase/database.types.ts`.
4. **Auth** (Dashboard → Authentication):
   - **Desative "Allow new users to sign up".** Usuários são criados só pelo dashboard (passo 5). Mesmo que alguém se cadastre, fica sem perfil e o RLS nega todo acesso, mas não há motivo para deixar a porta aberta.
   - Em *URL Configuration*: **Site URL** = `https://<site>` e, em **Redirect URLs**, `https://<site>/auth/confirm**` (e `http://localhost:3000/auth/confirm**` para desenvolvimento). É o callback do painel (`app/auth/confirm/route.ts`) para recuperação de senha.
   - **E-mail (SMTP).** O provedor de e-mail embutido do Supabase é só para testes: envia pouquíssimos e-mails por hora. Em produção, configure um SMTP próprio em *Authentication → Emails → SMTP Settings*. Sem isso, a recuperação de senha falha com "Muitas tentativas" depois de poucos envios.
   - Recomendado: em *Email Templates → Reset Password*, troque o link por `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery`. Assim o link funciona mesmo aberto em outro aparelho. O link padrão (`?code=`, PKCE) também é aceito, mas só funciona no mesmo navegador que pediu a recuperação.
5. **Usuários do painel.** Não há tela de usuários no painel: cada usuário (inclusive o primeiro ADMIN) é criado em *Authentication → Users → Add user → Create new user*, com e-mail, senha e **Auto Confirm User** marcado. Não use *Invite*: o painel não aceita links de convite. Depois, rode no SQL Editor:

   ```sql
   insert into public.profiles (id, name, role)
   select id, 'Bruno', 'ADMIN' from auth.users where email = lower('email@do-admin.com')
   returning id, name, role;
   ```

   O Auth grava o e-mail em minúsculas: comparar com `Fulano@...` não encontra ninguém e o `insert` passa sem inserir nada. O `returning` mostra a linha criada. Se o resultado vier vazio, o perfil não foi criado.

   Para um editor, troque `'ADMIN'` por `'EDITOR'` (é o papel padrão se a coluna for omitida). Papel, nome e desativação também só mudam pelo SQL Editor; pela API ninguém cria nem edita perfis, nem um ADMIN:

   ```sql
   update public.profiles set role = 'EDITOR' where id = (select id from auth.users where email = lower('email@do-usuario.com'));
   update public.profiles set deactivated_at = now() where id = (select id from auth.users where email = lower('email@do-usuario.com'));
   ```

   Desativar corta na hora todo acesso aos dados (RLS). O login continua possível, mas cai em `/painel/acesso-negado`. Para reativar, use `deactivated_at = null`. O banco não deixa rebaixar nem desativar o último ADMIN ativo (`AG003`).

   **Vendedor** (`'SELLER'`): só entra em Links comerciais e cria links com os próprios WhatsApp, que um ADMIN cadastra no painel. Por padrão ele usa os preços padrão dos modelos. Para permitir que negocie valores:

   ```sql
   insert into public.profiles (id, name, role)
   select id, 'Ana', 'SELLER' from auth.users where email = lower('email@do-vendedor.com')
   returning id, name, role;

   update public.profiles set can_customize_link_prices = true where id = (select id from auth.users where email = lower('email@do-vendedor.com'));
   ```

## Painel (`/painel`)

| Rota | Acesso |
| --- | --- |
| `/painel/login`, `/painel/recuperar-senha` | Visitantes. Com sessão, o proxy manda para `/painel`. |
| `/painel`, `/painel/configuracoes/senha` | Sessão + perfil ativo (qualquer papel). |
| `/painel/agenda`, `/painel/videos` | ADMIN e EDITOR ativos (`requirePanelStaff`). SELLER vai para `/painel/acesso-negado?motivo=perfil`. |
| `/painel/links` | ADMIN e SELLER ativos (`requirePanelLinkCreator`). EDITOR vai para `/painel/acesso-negado?motivo=perfil`. Canais de WhatsApp: só ADMIN. |
| `/painel/modelos` | Somente ADMIN ativo. EDITOR e SELLER vão para `/painel/acesso-negado?motivo=admin`. |
| `/painel/vendedores` | Endereço antigo: redireciona para `/painel/links`. |
| `/painel/acesso-negado` | Sessão sem perfil ativo (desativado ou sem `profiles`), ou papel sem acesso à área. |
| `/auth/confirm` | Callback do e-mail de recuperação de senha. |

Duas camadas: `proxy.ts` renova a sessão e faz a checagem otimista (há sessão?), e cada página/Server Action protegida chama `requirePanelUser()` (`lib/painel/session.ts`), que valida a sessão no Auth e lê o perfil do banco. Quem tem sessão mas não tem perfil ativo vai para `/painel/acesso-negado`, nunca de volta ao login, o que evita loop. O papel exibido vem sempre de `profiles.role`.

**Áreas de ADMIN** (`/painel/modelos`, os canais de WhatsApp e as ações deles): a página e cada Server Action chamam `requirePanelAdmin()` (sessão validada no Auth, perfil ativo e `role = ADMIN`, tudo lido no servidor), e o RLS (`private.is_admin()`) barra o que sobrar. A aplicação não usa a secret key.

## Testes do banco

`npm run test:db` executa a migration real num Postgres embutido (PGlite), com um shim do ambiente Supabase (`supabase/tests/support/testDb.ts`), e testa policies, triggers e funções diretamente em SQL, como cada papel. Não precisa de Docker.

**Contra o projeto real (opt-in).** `supabase/tests/real/` exercita a Agenda no Supabase configurado em `.env.local` (Auth, RLS, triggers e persistência de verdade). Os testes criam um ADMIN e um EDITOR temporários (`@example.com`) com a secret key e apagam tudo no final. Por criar dados, não rodam no `npm test`. O Auth limita logins por hora, então evite rodar várias vezes seguidas:

```sh
SUPABASE_REAL_TESTS=1 node --env-file=.env.local node_modules/vitest/vitest.mjs run --project db supabase/tests/real
```

## Decisões de modelagem

**Papéis.** `profiles.role` (`ADMIN` | `EDITOR` | `SELLER`) é lido por `private.current_app_role()`, que é `SECURITY DEFINER`, fica num schema não exposto pela API e só responde sobre o próprio `auth.uid()`. As policies usam `private.is_staff()` (ADMIN ou EDITOR: agenda, vídeos, configurações do site, nomes da equipe), `private.is_admin()` e `private.can_create_links()` (ADMIN ou SELLER), sem consultar `profiles` sob RLS, o que evita recursão. Desde a `20261018120100`, `is_staff()` não é mais "qualquer perfil ativo": o SELLER não herda nada da equipe. Usuário desativado ou sem perfil tem papel `NULL`, logo não tem acesso.

**Perfis.** Cada usuário só lê o próprio perfil (necessário para a autenticação), inclusive o ADMIN. Pela API ninguém cria nem edita perfis: não há policy nem privilégio de `INSERT`/`UPDATE` para `authenticated` (migration `20261014120000`). Tudo isso é feito pelo SQL Editor (passo 5). A Agenda, os Vídeos e os Modelos mostram "criado/excluído por" via `get_team_names()`, que devolve só id e nome para staff ativo.

**Troca de papel.** O banco não permite rebaixar ou desativar o último ADMIN ativo (`AG003`), nem pelo SQL Editor. Essa checagem é serializada com um advisory lock, então duas remoções simultâneas não zeram os ADMINs.

**Auditoria.** `created_by`, `updated_by` e `deleted_by`, além dos timestamps, são sempre definidos por trigger a partir da sessão. Valores enviados pelo cliente são descartados, e `created_*` é imutável.

**Soft delete.** "Excluir" um show é `update shows set deleted_at = <qualquer valor>`. O trigger grava `now()` e o usuário da sessão. Não existe privilégio nem policy de `DELETE` em `shows`. Um show excluído não pode ser editado, só restaurado (`deleted_at = null`). As consultas normais filtram `deleted_at is null`, e a lixeira filtra `deleted_at is not null` (`listShows({ status: 'deleted' })`).

**Financeiro.** Fica em `show_financial_entries`, separado de `shows`, e é acessível somente a ADMIN em todas as operações. `amount` é `numeric(12,2)` e **sempre ≥ 0**. O sinal vem do tipo: `CACHE` e `OTHER_REVENUE` somam, `EXPENSE` subtrai. Assim uma "Comissão de 50" é `EXPENSE / 50` e não existem valores negativos ambíguos. Não é permitido lançar em show excluído, e os relatórios ignoram shows excluídos.

**Relatórios.** `get_financial_report(from, to, group_by)` agrega por `day`, `week` (ISO, segunda-feira), `month` ou `year` e devolve cachês, outras receitas, despesas e líquido. Um EDITOR recebe erro `42501`, e não totais zerados.

**Site público.** Visitantes (`anon`) não têm privilégio em nenhuma tabela. A única porta é `get_public_agenda(from, to)`, que devolve somente `id`, `show_date`, `show_time`, `venue_name` e `venue_instagram` de shows ativos, sem join com o financeiro. O "mês atual" é calculado na aplicação (`currentMonthRange`, fuso `America/Sao_Paulo`) e não é armazenado.

**Exclusão de usuários.** Prefira desativar (`deactivated_at`, passo 5): o RLS corta o acesso na hora e o histórico fica. As FKs de auditoria apontam para `profiles` com `ON DELETE RESTRICT`. Por isso, apagar no Auth um usuário que já criou, editou ou excluiu algo **falha** e o histórico é preservado. Um usuário sem histórico pode ser apagado normalmente (o perfil sai em cascata).

**Índices.**

| Índice | Uso |
| --- | --- |
| `shows_active_date_idx (show_date, show_time) WHERE deleted_at IS NULL` | Agenda pública e listagem do painel por período, já ordenadas |
| `shows_deleted_at_idx (deleted_at DESC) WHERE deleted_at IS NOT NULL` | Lixeira do painel |
| `show_financial_entries_show_id_idx (show_id, created_at)` | Lançamentos de um show e join do relatório |
| `seller_links_seller_idx (seller_id, created_at DESC)` | Histórico de links comerciais de um vendedor |

As FKs de auditoria não têm índice próprio. As tabelas são pequenas, e o único uso dessas colunas em filtro seria a exclusão de usuários, que é rara.

**Vídeos.** `public.videos` alimenta a seção VIDEOS. Cada vídeo tem uma **classificação editorial** (`placement`), independente da orientação: `main` (principal da Home, vertical ou horizontal), `secondary` (Home, depois do principal, até o limite do dispositivo) ou `gallery` (só no "Ver mais"), além de `active` (desativado sai da Home e do "Ver mais", mas continua cadastrado). A ordem é `position`, trocada por `move_video(id, 'up'|'down')` dentro da classificação (quem muda de classificação vai para o fim dela). **No máximo um principal:** o índice único parcial `videos_single_main` garante isso mesmo com atualizações simultâneas, o trigger dá uma mensagem clara (`AG006`) e a troca é feita por `set_main_video(id)`, que (sob advisory lock, numa transação) rebaixa o anterior a primeiro secundário e promove o novo; vídeo inativo não pode ser promovido. Sem principal, a Home começa pelos secundários; nada é promovido automaticamente. **Limites da Home** ficam em `public.video_settings` (uma linha só): `home_limit_desktop` (≥ 768px, computador e tablet) e `home_limit_mobile` (celular), inteiros de 1 a 12, editados por staff; o valor inicial (3 e 3) é o comportamento anterior. A regra de exibição (`lib/videos/gallery.ts`): só ativos → principal primeiro → secundários na ordem → corta no limite (cada vídeo conta 1, principal incluído) → o que sobrou e os `gallery` vão para o "Ver mais". YouTube guarda só o ID; arquivos são caminhos do site (`/videos/...`) ou uploads do painel no bucket público `videos` do Storage (50 MB, mp4/jpg/png/webp; envio e exclusão só por staff). O site lê apenas `get_public_videos()` (só ativos) e `get_public_video_settings()`. A migration `20261011120000` importou os 7 vídeos de `videoList.ts`; a `20261013120000` converteu os 3 que estavam na Home em secundários e os 4 do "Ver mais" em `gallery`, sem escolher principal (a Home fica igual até o painel escolher um).

**Modelos de show.** `public.show_models` alimenta a seção NOSSO SHOW: nome, duração (a linha abaixo do nome), descrição opcional, `price numeric(10,2) > 0` em reais e `active`. Só os ativos aparecem no site, na ordem de `position` (desempate por `created_at` e `id`), trocada por `move_show_model(id, 'up'|'down')`. O nome é único sem diferenciar maiúsculas, porque ele vai na mensagem do WhatsApp. Não há exclusão física: desativar tira o modelo do site e preserva o registro. **Preço só na versão comercial:** `get_public_show_models()` devolve nome, duração e descrição, **sem preço** (é o que a Home estática usa, então nem o HTML nem os dados de hidratação têm valores). `get_commercial_show_models(code)` devolve os mesmos modelos com o preço, só para o código de um vendedor ativo; é chamada no servidor pela Server Action `loadCommercialShowModelsAction` (`app/actions.ts`), a partir do cookie do link. A migration `20261012120000` importa os 4 formatos que estavam em `components/Show/showContent.ts`, de forma idempotente (pelo nome). Cada alteração no painel chama `revalidatePath("/")`, então a Home estática é regenerada sem deploy.

**Vendedores e links comerciais (histórico: `sellers` e os links permanentes foram removidos na `20261018120300`; o fluxo de cookie e do "Voltar ao WhatsApp" continua igual, só que sempre por link temporário).** `public.sellers` guardava contatos comerciais, que não são usuários do painel: nome, `whatsapp` (só dígitos, DDI + DDD + número, validado também no banco, com regra própria para +55) e `code`. O código tem 12 caracteres hexadecimais aleatórios, é gerado pelo trigger, é imutável e não depende do nome nem do telefone. O link é `/r/<code>` (`app/r/[code]/route.ts`): confere o código com `get_seller_link(code)` (que devolve só o status e, se ativo, o número), grava o código num cookie de sessão `bb_vendedor` e abre o site. Código malformado, inexistente, de vendedor inativo ou banco fora do ar leva a `/link-invalido?motivo=…` e **apaga** o cookie (sem preços e sem encaminhar a outro vendedor). **Regra de atribuição:** só a abertura de um link muda o vendedor; o último link válido aberto prevalece, e navegar pelo site sem link nunca altera nada. O cookie não autoriza nada sozinho: a versão comercial (valores, escolha do formato, data/horário opcionais) só é liberada depois de o servidor conferir o código no banco; se o vendedor foi desativado, a Server Action apaga o cookie e a seção volta a ser a pública. O "Voltar ao WhatsApp" é montado no servidor (`app/actions.ts`): lê o cookie, confere de novo o vendedor e o modelo, valida data (`AAAA-MM-DD`, só datas reais, sem regra de antecedência) e horário (`HH:MM`), e recusa se o nome ou o valor mudaram desde que a página foi carregada. A mensagem inclui saudação, modelo, valor em reais e, só se informados, data e horário. Sem link comercial, a seção NOSSO SHOW fica só informativa, sem valores (o contato segue na seção CONTATO). Não há exclusão física: desativar invalida o link e permite reativar.

**Links comerciais temporários (migration `20261017120000`).** (Histórico: a criação descrita aqui, por vendedor sem conta, foi substituída pela `20261018120100`; ver "Links comerciais por usuário". Validade, imutabilidade e fluxo público continuam valendo.) Em Vendedores → "Criar link", o ADMIN gerava para um vendedor um link `/r/<code>` com **valores próprios por modelo** e validade de no máximo 7 dias. Os preços padrão (`show_models.price`) não mudam, e mudar o padrão depois não afeta nenhum link já gerado.

- **Tabelas.** `public.seller_links`: `seller_id` (FK `sellers`, restrict), `code` (16 hex, 64 bits aleatórios, gerado pelo trigger, `unique`, formato `^[a-z0-9]{8,32}$`), `label` opcional (1 a 80, só no painel), `expires_at timestamptz`, `active`, `deactivated_at`/`deactivated_by`, `created_by`/`created_at`. Checks: `expires_at > created_at` e `expires_at <= created_at + 168 horas`; desativação consistente. `public.seller_link_prices`: PK `(link_id, model_id)`, FKs restrict, `price numeric(10,2) > 0` (mesma regra e precisão de `show_models.price`).
- **Unicidade do código também entre tabelas.** O trigger `private.link_code_is_free()` (em `sellers` e `seller_links`, serializado por `pg_advisory_xact_lock`) impede que um código exista nas duas tabelas, inclusive se informado pelo SQL Editor (`23505`). Os geradores (`new_seller_code`, `new_seller_link_code`) já evitam códigos das duas tabelas, e o tamanho diferente (12 × 16) os separa na prática.
- **Criação atômica.** Só por `create_seller_link(p_seller_id, p_label, p_validity, p_expires_at, p_prices jsonb)`, `SECURITY DEFINER` com `search_path = ''`, que exige ADMIN ativo (`42501`) e grava o link e todos os preços numa transação: qualquer erro desfaz tudo. `p_validity`: `24h`, `3d` ou `7d` (o banco calcula `now() + 24/72/168 horas`, ignorando `p_expires_at`) ou `custom` (`p_expires_at` precisa ser `> now()` e `<= now() + 168 horas`). `p_prices` = `[{ "model_id", "price" }]`, exatamente um por modelo **ativo** (sem faltar, repetir, sobrar nem usar inativo), preço número `> 0`, até 2 casas (sem arredondar) e `<= 99999999,99`. Vendedor precisa estar ativo. Autoria vem de `auth.uid()`.
- **Imutável.** `authenticated` só tem `SELECT` (RLS: ADMIN) nas duas tabelas; `anon`, nada. Nem o SQL Editor altera preço, validade, código, vendedor ou identificação, nem apaga (trigger, `AG007`). A única mudança é a desativação, só por `deactivate_seller_link(id)` (ADMIN, idempotente, sem volta, recusada se o link já expirou). Valor errado = novo link.
- **Validade.** Expirado quando `now() >= expires_at` (precisão de microssegundos; o prazo personalizado é escolhido até o minuto). O painel interpreta data e hora no fuso `America/Sao_Paulo` (`zonedTimeToInstant`, base de fusos do runtime) e envia o instante absoluto; o banco é quem decide se está no intervalo.
- **Histórico.** `get_seller_links()` (SECURITY INVOKER + checagem de ADMIN) devolve todos os links, mais recentes primeiro, com `status` calculado pelo relógio do banco (`active`, `expired`, `revoked` = desativado antes de expirar) e os preços gravados (com o nome atual do modelo). Nada é apagado.
- **Site público.** `get_seller_link(code)` foi recriada (o retorno mudou): mantém `active` e `whatsapp` nas mesmas posições e acrescenta `link_kind` (`seller` | `link`), `status` (`active`, `inactive` = vendedor desativado, `expired`, `revoked`, `invalid` = link sem preços) e `expires_at` (só se ativo). `get_commercial_show_models(code)`: link permanente → preço padrão; link temporário ativo, dentro da validade e de vendedor ativo → **só** os modelos e preços gravados no link (modelo criado depois não entra; desativado sai; nunca cai no preço padrão).
- **Fluxo.** `/r/<code>` de link temporário válido grava `bb_vendedor` com `Max-Age` até a expiração. Expirado, desativado, de vendedor inativo ou inconsistente → **apaga o cookie e abre o site público** (`/`, sem preços), sem página de erro; links permanentes continuam como antes. A Server Action da versão comercial reconfere tudo a cada carregamento e, se a página ficar aberta até o prazo, o navegador pede de novo e os valores saem ("Esta proposta expirou"). O "Voltar ao WhatsApp" reconfere link, validade, vendedor, modelo e o preço exato do link; expirado → mensagem própria (não "formato atualizado"), e se o link expirar entre as duas leituras o servidor reconfere antes de responder.

**Aplicar a `20261017120000` no projeto real.** (1) Confirme que `20261012120000`, `20261013120000`, `20261014120000` e `20261015120000` já foram aplicadas (por exemplo, `select to_regprocedure('public.get_commercial_show_models(text)'), to_regclass('public.agenda_settings');` não deve devolver nulos). (2) Rode `20261017120000_seller_links.sql` uma vez no SQL Editor (ou `npx supabase db push`). Ela não altera nem apaga dados: só cria tabelas/funções, recria `get_seller_link` e substitui `get_commercial_show_models` e `new_seller_code`. (3) Rode `npm run db:types` (os tipos foram editados à mão nesta mudança). (4) Valide: `select * from public.get_seller_link('<código permanente>');` deve devolver `active = true, link_kind = 'seller', status = 'active'`; crie um link no painel e abra `/r/<código>` numa janela anônima. (5) Só então publique o código. Se o código for publicado antes, os links permanentes e o site continuam funcionando, mas a página Vendedores do painel mostra "Não foi possível carregar os vendedores" (o histórico de links vem de `get_seller_links`, que ainda não existe).

**Links comerciais por usuário (migrations `20261018120000` e `20261018120100`).** A geração de links saiu de Vendedores e virou o módulo **Links comerciais** (`/painel/links`). Quem cria é o usuário logado (ADMIN ou SELLER), com um WhatsApp dele, escolhido obrigatoriamente em cada link.

- **Canais.** `public.whatsapp_channels`: `owner_id` (perfil ADMIN/SELLER ativo), `whatsapp` (mesma validação de `sellers.whatsapp`, via `private.is_valid_whatsapp`), `label`, `active`, `is_primary` (no máximo um por usuário; só ordena a lista, nunca pré-seleciona) e `redirect_channel_id`. Único por `(owner_id, whatsapp)`; o mesmo número pode estar em usuários diferentes. Só ADMIN cadastra; cada ADMIN lê e altera só os canais que **ele** cadastrou (`created_by`, migration `20261020120000`), e o dono só lê os próprios (RLS + trigger). No painel, a gestão fica em **Configurações** (só ADMIN), não mais em Links comerciais. Número e dono são imutáveis e nada é apagado (`AG008`).
- **Criação.** Só por `create_commercial_link(p_channel_id, p_label, p_validity, p_expires_at, p_items jsonb)`, `SECURITY DEFINER`: exige ADMIN/SELLER ativo, canal **ativo do próprio usuário** (canal de outro usuário, inexistente ou desativado → mesmo erro `42501`, sem revelar qual) e um ou mais modelos ativos (`[{ "model_id", "price"? }]`). Sem `price`, grava o preço padrão vigente. Preço diferente do padrão só com permissão (`42501` sem ela): ADMIN sempre; SELLER só com `profiles.can_customize_link_prices = true` (falso por padrão, alterado pelo SQL Editor). O número e a identificação do canal são copiados do banco para o link (`seller_links.whatsapp`, `channel_label`); o cliente nunca informa o destino. Cada preço guarda também o padrão da época (`seller_link_prices.default_price`). Validade e imutabilidade seguem as regras da `20261017120000`.
- **Isolamento.** `get_seller_links()` e o RLS de `seller_links`/`seller_link_prices`: ADMIN vê todos; SELLER só os que criou. `deactivate_seller_link(id)`: ADMIN qualquer um; SELLER só os próprios (link de outro usuário responde como inexistente). `get_link_show_models()` e `get_commercial_link_permissions()` servem o formulário; `get_whatsapp_channel_owners()` é só para ADMIN.
- **Canal desativado.** Nenhum link novo pode usá-lo. Os links já criados com ele ficam com status `inactive` (sem WhatsApp e sem valores no site) até o ADMIN: (a) reativar o canal, e os links voltam ao número original; ou (b) apontar o canal desativado para outro canal ativo (`redirect_channel_id`), e os contatos passam a ir para esse número. Dono desativado tem o mesmo efeito de canal desativado. O número gravado no link nunca muda; o histórico mostra o original e o destino atual. O redirecionamento é de um nível só: se o canal de destino for desativado depois, os links voltam a `inactive`.
